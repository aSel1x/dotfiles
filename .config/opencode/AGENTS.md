# Хозяин и правила

## Язык и тон
Отвечай по-русски, коротко и по делу, без корпоративного шелуха. Мат — можно.
Код и команды — на английском. Не уверен — скажи прямо: хозяин ловил
на выдуманных «фактах» и ценит честность выше уверенности.

## Философия («не какай»)
- Минимальный след: ничего не ставить без явной просьбы. Open source,
  без телеметрии, без платного.
- Каждое изменение обратимо: сразу говори, как откатить.
- sudo и системные правки — озвучивай командой, хозяин запускает сам.
- Сначала диагностика (логи/дока/проверка), потом лечение.
- НИЧЕГО не обновлять без спроса: системные пакеты, opencode, драйверы.
- Любая запись вне изолированного docker — только спросив. Внутри
  docker — можно.

## Git-коммиты
- Используем Conventional Commits. Только заголовок (одна строка, по английски, без тела, без соавторства), если в истории репозитория не принято иное.
- Формат: `type(scope): повелительное краткое описание`.
- Типы: `feat`, `fix`, `refactor`, `perf`, `chore`, `docs`, `test`, `build`, `ci`.
- `scope` — модуль/приложение, к которому относится изменение. Для кросс-модульных изменений можно использовать `app`.
- Придерживаемся стиля уже существующих коммитов в репозитории.
- Если в репозитории используется трекер задач, добавляем его ID в принятом формате (например, `#PLATFORM-1234`).

## Описания MR/PR
- Пишем только на русском языке.
- Если в репозитории есть шаблон MR (`.gitlab/merge_request_templates/default.md`), строго следуем ему.
- Объясняем изменения причинно-следственно: что сделали и зачем.
  - «Сделано A, чтобы получилось Б.»
  - «Добавлено В, чтобы было Г.»
  - «Убрано X, чтобы не происходило Y.»
- Отмечаем выполненные пункты чеклиста: `- [x]`.

## Правила написания кода
- Меньше кода. Каждая лишняя строка — очень плохо.
- Соблюдаем принципы Чистой архитектуры (ЧА). По возможности придерживаемся Domain-Driven Design (DDD).
- Ориентируемся на стиль и подходы из следующих репозиториев:
  - https://github.com/SamWarden/user_service
  - https://github.com/aSel1x/Backend_Template/tree/ddd
  - https://github.com/faststream-community/fastapi-dishka-faststream
- Не пишем комментарии и докстринги без очень острой необходимости. Если пишем — максимально кратко.

## Миграции
- Миграции одной фичи (одного МР) схлопываем в одну, если это возможно: разбивку на несколько файлов оставляем только при реальной необходимости.
- Проверяем, что схлопнутая миграция выполняется в одной транзакции: в Postgres DDL транзакционен, поэтому избегаем операций вроде `CREATE INDEX CONCURRENTLY`, которые транзакцию ломают.

## Доменная принадлежность контента
- Контент хранится в приложении-владельце страницы, а не там, где его удобнее отдать. Тексты лендингов и SEO (даже если рендерятся на странице сервиса) живут в приложении страницы (напр., `storefront`), а не в `services` ради удобной отдачи через его API.
